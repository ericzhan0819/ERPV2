## 正式契約

- Login 與 `/api/me` 取得的完整 `UserResource` 都直接進入 Auth Context，包含 `username` 與 `must_change_password`。
- Auth Context 提供 `updateProfile()`、`updatePassword()`；成功回應只可更新同一個仍在登入中的 User。
- 登出 pending／blocked、已登出或不同 User 的過期 self API 回應，不得恢復或覆蓋 Context，且 wrapper 會 reject `StaleCurrentUserResponseError`，呼叫頁不得誤走成功提示或導向。
- `must_change_password=true` 的一般 protected route 固定導向 `/change-password`。
- `/change-password` 使用 `passwordChangeOnly` route gate：flag=true 才可顯示，flag=false 回 Dashboard，因此不會形成 redirect loop；暫存頁不掛 AppLayout／Sidebar。
- Route 判斷順序固定為 loading → logout pending／blocked → authentication → password-change gate → role。
- API response interceptor 只有在 HTTP 409 且 response `code` 精確等於 `PASSWORD_CHANGE_REQUIRED` 時通知 Auth Context；其他一般 409 維持原頁面既有錯誤處理。
- 收到 password-required 通知時，由已測純函式判斷是否把目前登入者同步為待改密碼，不改動 logout marker；登出安全狀態永遠優先。
- API error handler 的預設通知、訂閱與 unsubscribe 鏈可在既有 Node Vitest 環境執行；production 仍使用同一個 browser `window` EventTarget。

- 未登入導 Login。

- logout pending／blocked 先於 auth redirect。

- 被拒絕的 self API 回應會拋出專用錯誤，不會向未來頁面回報成功。

## Adversarial Review Follow-up

2026-07-26 收到 3 項 findings 後逐項查證：

- F1 有效：原實作會導向尚未掛載的 `/change-password`，React Router 無 match 時形成無登出出口的空白頁。已加入 `passwordChangeOnly` 暫存 route，僅提供說明、Theme Toggle 與安全登出；未以 catch-all 製造 redirect loop。

- F3 有效：原 `updateProfile()`／`updatePassword()` 忽略 Context update 被拒絕的結果，未來頁面可能在登出競態中誤走成功流程。現在被拒絕時固定拋出 `StaleCurrentUserResponseError`，並補上直接測試。
