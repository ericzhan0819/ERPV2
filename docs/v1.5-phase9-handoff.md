## 正式契約

- Login 與 `/api/me` 取得的完整 `UserResource` 都直接進入 Auth Context，包含 `username` 與 `must_change_password`。
- Auth Context 提供 `updateProfile()`、`updatePassword()`；成功回應只可更新同一個仍在登入中的 User。
- 登出 pending／blocked、已登出或不同 User 的過期 self API 回應，不得恢復或覆蓋 Context，且 wrapper 會 reject `StaleCurrentUserResponseError`，呼叫頁不得誤走成功提示或導向。
- `must_change_password=true` 的一般 protected route 固定導向 `/change-password`。
- `/change-password` 使用 `passwordChangeOnly` route gate：flag=true 才可顯示，flag=false 回 Dashboard，因此不會形成 redirect loop；暫存頁不掛 AppLayout／Sidebar。
- Route 判斷順序固定為 loading → logout pending／blocked → authentication → password-change gate → role。
- API response interceptor 只有在 HTTP 409 且 response `code` 精確等於 `PASSWORD_CHANGE_REQUIRED` 時通知 Auth Context；其他一般 409 維持原頁面既有錯誤處理。
- 收到 password-required 通知時，由已測純函式判斷是否把目前登入者同步為待改密碼，不改動 logout marker；登出安全狀態永遠優先。
- API error handler 使用 module-private `EventTarget`；預設通知、訂閱與 unsubscribe 在 production／Node Vitest 執行完全相同的程式路徑，不對 `window` 暴露內部事件名稱。
- 每次成功登入會寫入新的跨分頁 auth session version。其他仍有 User Context 的 idle 分頁收到版本變更，或收到既有 logout marker 被清除時，會立即讓舊 Context 失效並導回 Login，避免 cookie 已切換帳號後仍以舊表單呼叫 self write API。
- 跨分頁登入事件不得解除 logout pending／blocked；沒有登入 Context 的分頁不需額外處理。

測試直接涵蓋：

- 未登入導 Login。
- Login／me 帶回待改密碼 flag 時，營運 route 導向強制頁。
- 強制頁 route gate 不循環導向，完成改密碼後回 Dashboard。
- 待改密碼判斷先於 role gate。
- logout pending／blocked 先於 auth redirect。
- 只有精確的 `409 + PASSWORD_CHANGE_REQUIRED` 會通知 Auth Context，且預設事件訂閱／清理鏈實際執行。
- password-required listener guard 只接受 idle 且已登入、尚未標記的使用者。
- self API 完整回應只更新同一個 idle session；登出中、已登出或不同 User 回應被拒絕。
- 被拒絕的 self API 回應會拋出專用錯誤，不會向未來頁面回報成功。
- 其他分頁登入時，只有仍持有 User 的 idle 分頁會失效；未登入分頁與 logout pending／blocked 狀態不受覆蓋。

## Adversarial Review Follow-up

2026-07-26 收到 3 項 findings 後逐項查證：

- F1 有效：原實作會導向尚未掛載的 `/change-password`，React Router 無 match 時形成無登出出口的空白頁。已加入 `passwordChangeOnly` 暫存 route，僅提供說明、Theme Toggle 與安全登出；未以 catch-all 製造 redirect loop。
- F2 有效：原測試只覆蓋純 classifier 與注入的 notify，沒有執行預設 EventTarget 接線，Provider listener guard 也是未測的獨立實作。已讓事件 target 在 Node Vitest 使用原生 `EventTarget`，直接測試預設通知／訂閱／unsubscribe，並把 listener guard 抽成 `applyPasswordChangeRequired()` 純函式補回歸。
- F3 有效：原 `updateProfile()`／`updatePassword()` 忽略 Context update 被拒絕的結果，未來頁面可能在登出競態中誤走成功流程。現在被拒絕時固定拋出 `StaleCurrentUserResponseError`，並補上直接測試。

第二輪 review 新增 2 項 Low findings，均確認有效並修正：

- F4 有效：password-required 事件原掛在全域 `window`，同頁外部程式可無必要地觸發 fail-closed 導流，且 Node 測試與 production 使用不同 target。已改為無條件建立 module-private `EventTarget`，消除全域入口與環境分支。
- F5 有效：其他分頁登入不同帳號後，舊分頁可能繼續顯示原 User，導致 `/api/me/profile` 依新 cookie 寫到錯誤帳號。除了處理 logout marker 的 `newValue=null`，每次登入另寫新的 auth session version，確保 logout marker 原本不存在時仍會產生 storage event；舊 idle User Context 立即清空，logout pending／blocked 則維持優先。storage event 分類與狀態判斷已抽為純函式並補直接測試。
