## 正式契約

### Admin 建立員工

`POST /api/users` 不接受 `username` 或 `must_change_password`。即使直接呼叫 `UserService::createUser()`，服務仍明確覆寫為：

```text
username = null
must_change_password = true
```

回應沿用 `UserResource`，會回傳上述狀態，但不會回傳 password 或 hash。

User insert 與 Audit Observer 寫入位於同一個 database transaction。若稽核寫入失敗，帳號建立會 rollback，不會留下可登入但無建立稽核的帳號。

### Admin 重設密碼

`POST /api/users/{id}/reset-password` 只接受新密碼；任何 `must_change_password` 鍵值都回 422。成功時：

```text
password = 新密碼 hash
must_change_password = true
```

密碼與 flag 使用同一次 `save()`，並包在同一個 database transaction。若 Audit Observer 無法寫入稽核紀錄，整個重設會 rollback，舊密碼與舊 flag 都保留。

Laravel Sanctum 的 stateful Session 會保存登入時的密碼 hash。Admin reset 後，每個既有 stateful Session 在各自下一個請求會因 hash 不符被清空並回 `401 Unauthenticated`，不會在舊 Session 內讀到 flag 或進入第 6 部分的 `409` gate。使用者必須以新密碼重新登入；登入回應才會帶 `must_change_password=true`，再由前端導向強制修改密碼頁。

第 6 部分 Middleware 處理的是「以預設／重設密碼成功登入後，Session 仍有效但 flag=true」的請求。第 6 與第 7 部分必須同輪交付，避免先啟用 gate 卻沒有 self password endpoint 可清除 flag。

### 既有帳號

- v1.5 migration 的 database default 仍為 `false`。
- 不依 `created_at`、Email、角色或其他既有資料推測誰需要改密碼。
- `AdminUserSeeder` 仍明確維持 `must_change_password=false`，不會把開發管理員鎖住。
