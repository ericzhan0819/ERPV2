## 測試契約

### Schema／User

- `username` nullable、unique、正規化與大小寫唯一性。
- `must_change_password` database default 為 `false`，既有使用者不做推測式回填。
- Factory／Seeder 可明確建立預設、待改密碼與具 username 狀態。
- Migration 可 rollback 後重新執行。
- Admin 建立與重設密碼固定設為 `must_change_password=true`，payload 不可覆寫。
- Username stale validation 與真正 database race loser 都轉為欄位 validation error。
- `UserResource` 回傳完整安全欄位，原始 JSON 不含 password／remember token。

### Auth

- Email／username 登入、trim／case normalization、通用錯誤與停用帳號。
- Stateful 登入成功 regenerate Session ID 並留下 Authentication Audit。
- 非 stateful login 在查詢帳號、驗證密碼或異動 limiter 前固定回安全的 419；
  正確／錯誤密碼回應相同，既有失敗額度不會被清除。
- 非 stateful logout 不存取不存在的 Session store，維持公開冪等 200。
- 即使 `personal_access_tokens` table 存在格式正確的 legacy token，Bearer request
  仍固定回 401，token 的 `last_used_at` 不會更新。
- Username／Email alias 共用 canonical account 與 identifier + IP limiter。
- IP-wide limiter、blocked request 不再查詢／驗證、成功登入清理邊界。
- `429` 保留正整數秒數的 `Retry-After` header。

### Password Gate／Self Account

- 待改密碼狀態只放行 `/api/me`、logout、self profile 與 self password。
- 所有 authenticated 營運路由由 route inventory test 保護，不得漏掛 gate。
- Gate 固定回 `409` 與 `PASSWORD_CHANGE_REQUIRED`，並先於 role、model binding 與 policy。
- 未登入仍回 `401`，停用帳號仍由 active middleware 優先回 `403`。
- Sales／未知角色不能藉下游 403 繞過 gate；flag=false 的未知角色仍由 role middleware
  fail-closed，只能使用既有安全 self account 邊界。
- Admin／manager／sales／未知角色只能修改自己的 name、username 與 password。
- Email、role、active、員工欄位及其他 workflow 欄位只要出現在 self payload 就回 `422`。
- Current password、confirmation、不可沿用原密碼、flag clear、Session regenerate 與 Audit 密碼遮蔽均有直接測試。

## Adversarial Review Follow-up

Review 提出 1 High、2 Medium、1 Low finding，逐項回到 runtime 與測試查證後均有效：

- F1：非 stateful login 原本在正確憑證清除 limiter 後才因缺少 Session store 回 500，
  同時形成密碼 oracle 與 authentication audit 缺口。現由 `AuthService` 在任何帳號查詢、
  credential check 或 limiter 異動前拋出專用例外，`AuthController` 固定轉為不含 trace 的
  `419 {"message":"工作階段無效，請重新整理後再試"}`。正確／錯誤密碼均鎖定相同回應，
  預先累積的 limiter 次數維持不變且不建立 authentication audit。
- F1 logout：`logout()` 只在 `request()->hasSession()` 時 invalidate／regenerate token；
  未登入且非 stateful 的公開 logout 維持精確 200。
- F2：Login 使用 `Attempting` event 取樣 credential check 當下的 server Session ID；
  成功登入必須 `assertNotSame`，失敗登入必須 `assertSame`。Self password 則在 User
  password update event 取樣；profile update 作為 `assertSame` 負向對照。
- F3：MariaDB 競態移除 test-only `setUsername()`，winner／loser 均呼叫正式
  `updateCurrentProfile()`，直接涵蓋其 transaction 與 duplicate conversion。
- F4：Password Gate priority 改以 `/api/users` admin-only route 驗證 flagged sales／
  unknown role 均先回 409；另鎖定未 flagged unknown role 回 403。

第二輪 review 提出 1 Medium、1 Low finding，均完成最小修正：

- F5：`EnsureUserIsActive` 停用分支改為只有 `request()->hasSession()` 時 invalidate，
  先消除任何無 Session 認證來源可能觸發的 500。後續 session-only 決策使 Bearer token
  統一在 auth middleware 回 401；此守衛仍作為 middleware 的防禦性邊界。
- F6：保留既有公開 logout 的冪等 200 契約，但非 stateful 請求不再宣稱「已登出」，
  改回 `{"message":"無可登出的工作階段"}`。API 明確記錄此路徑是 no-op，不代表其他
  Session 已被銷毀；stateful logout 仍實際 invalidate Session 並回「已登出」。

### Session-only 認證決策

第二輪 review 的 residual risk 經使用者明確確認後，正式採用：

- ERPV2 只支援 Sanctum SPA cookie／Session，不支援 personal access token／Bearer token。
- `User` 移除 `HasApiTokens`，正式程式不具 `createToken()` 或 token relationship。
- 保留既有 `personal_access_tokens` table，不為此決策新增破壞性 migration；既有 row
  只是不再具認證能力。
- 回歸測試直接插入有效格式、`abilities=["*"]` 的 legacy token，確認
  `auth:sanctum` 仍回 401 且不更新 `last_used_at`。
- 不新增 token 發放、撤銷、CSRF 例外、能力或稽核 actor 等平行認證功能。
