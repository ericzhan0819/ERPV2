## 測試契約

### Auth

- Login 顯示 config 標題與副標，識別欄位是 `type=text`、`name=login` 與
  `autocomplete=username`。
- Email 與 username 都會送進 Auth Context；既有 API contract test 再鎖定最終 HTTP
  payload 使用 `login`，不回退成 `email`。
- 登入成功依 `must_change_password` 導向 Dashboard 或強制改密碼頁。
- 既有 API interceptor 的 `409 + PASSWORD_CHANGE_REQUIRED` 契約，現另由整合測試確認
  Auth Context 收到事件後會把受保護畫面導向強制改密碼頁。
- 登出會走 Auth Context、呼叫 logout API、留下 completed marker 並回 Login。

### Account

- 由 `/api/me` 載入目前使用者，Email／角色只讀呈現。
- 修改名稱後，self profile payload 正確送出，Auth Context 與 Header 名稱立即更新。
- Username 新增、更新與清除均經實際表單提交；清除明確送出 `null`。
- Username 後端 validation error 顯示於欄位並設定 `aria-invalid`。
- 密碼 confirmation 不符在前端阻擋；後端目前密碼錯誤回到對應欄位。
- 密碼成功 payload 包含 current password／password／confirmation，成功後三欄清空。

### Config／Theme

- Login 實際顯示 `appConfig.systemName` 與 `appConfig.loginSubtitle`。
- Sidebar 實際顯示 `appConfig.systemShortName`。
- 既有 source／Vite plugin contract test 持續鎖定 `document.title` 與 build-time HTML title
  皆來自 `appConfig.browserTitle`，並涵蓋 HTML escaping。
- Theme Toggle 以實際 Theme Provider 驗證 light → dark 切換與可存取名稱更新。

## Adversarial Review Follow-up

Review 提出 1 個 Medium 與 1 個 Low finding，逐項回到 Auth Provider、production route tree
與既有測試查證後均有效，已完成最小測試補強：

- 登出 happy path 原本無法證明兩次 logout 都失敗時會進入安全的 blocked 狀態。現以實際
  App Layout／Auth Provider 驗證第一次失敗後會刷新 CSRF 並重試；第二次仍失敗時固定顯示
  「登出尚未完成」阻擋畫面、寫入 `LOGOUT_STATE_KEY=failed`、不導向 Login，且不會誤寫
  completed。
- Login flag 與 API 409 導向原本使用裸文字 route stub，無法證明 production
  `passwordChangeOnly` gate 接受 Context 中的新 flag。現改為與 `App.tsx` 相同的
  `ProtectedRoute passwordChangeOnly + PasswordChangeRequired` 組合，並斷言真實強制改密碼
  頁標題可渲染，直接排除目的地 gate 導回 Dashboard 的迴圈。
