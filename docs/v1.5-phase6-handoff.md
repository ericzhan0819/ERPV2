## 正式契約

### Password Change Required Gate

Authenticated 營運路由依序執行：

```text
auth:sanctum
→ active
→ password.changed
→ role（若有）
→ route model binding
→ policy（若有）
```

`must_change_password=true` 時固定回：

```json
{
  "message": "請先修改密碼",
  "code": "PASSWORD_CHANGE_REQUIRED"
}
```

HTTP status 為 `409 Conflict`。Gate 位於角色檢查與 route model binding 前，避免待改密碼帳號利用 `403`／`404` 差異枚舉營運資源。停用帳號仍優先回既有 `403`，未登入仍由 Sanctum 回 `401`。

唯一 allowlist：

```text
GET   /api/me
POST  /api/logout
PATCH /api/me/profile
PATCH /api/me/password
```

`POST /api/logout` 維持既有公開冪等路由；Login、Sanctum CSRF 與 `/api/public/vehicles*` 不受 gate 影響。測試會掃描所有 `auth:sanctum` 路由，除三個 self account 例外外都必須帶 gate，避免未來新增 authenticated route 時意外漏保護。

### Self Profile

`PATCH /api/me/profile` 只操作 `$request->user()`，不接受 target user id。

- 必須完整提交 `name` 與 `username`。
- `username=null` 或空字串代表明確清除；非 null 值沿用共用正規化、格式與 unique 規則。
- Email、role、admin／active 狀態、員工欄位、`must_change_password` 與 password 只要出現在 payload 就以 `missing` rule 回 `422`。
- Database unique race 仍轉為 `username` 欄位 `422`，不回未處理的 `500`。
- Name 與 username 使用單一 `save()`，並與 User Audit 位於同一個 transaction；Audit 失敗時完整 rollback。
- 成功回傳更新後 `UserResource`，不含 password／remember token。

### Self Password

`PATCH /api/me/password` 只操作 `$request->user()`：

- `current_password` 必須通過 Laravel `current_password:web` rule。
- 新密碼 required、string、至少 8 字元、不可與目前密碼相同且 confirmed。
- Password 與 `must_change_password=false` 使用單一 `save()`，並與 User Audit 位於同一個 transaction。
- 請求具有 Session 時，成功後 regenerate 目前 Session ID；下一個 stateful request 仍保持登入，不會被 Sanctum `AuthenticateSession` 踢出。沒有 Session store 的 authenticated 呼叫不會在資料已 commit 後因讀取 Session 而回 `500`。
- 成功回傳更新後 `UserResource`。
- 其他帳號流程欄位使用 `missing` rule 明確回 `422`，不會靜默忽略成假成功。
- Audit 只記錄 `must_change_password` 狀態變更，不含明文、hash、目前密碼或 confirmation。

## 部署與後續邊界

本階段是後端完整安全切片，但不是可單獨部署的 v1.5 使用者體驗。現有前端尚未處理 `PASSWORD_CHANGE_REQUIRED`，也沒有自助密碼表單；待改密碼帳號在瀏覽器內會被營運 API 阻擋，但無法透過 UI 完成解鎖。

因此第 5～7 部分仍不得單獨部署到正式環境，尤其是只有單一 admin 的環境。下一部分從 `PLAN_v1.5.md` 第 8 部分開始，接續 API types，之後完成 Auth Context、集中 409 導流與強制改密碼／我的帳號頁。

## Adversarial Review Follow-up

2026-07-26 收到 1 項中度與 3 項低度 findings 後逐項重現：

- F1 有效：原規則允許新密碼等於目前密碼，會在預設密碼未真正更換時清除 `must_change_password`。已新增 `different:current_password`、繁體中文欄位錯誤與 flagged user 回歸測試。
- F2 有效：沒有 Session store 的 authenticated 測試路徑會在交易 commit 後才因無條件讀取 Session 回 `500`。已改為只有 `hasSession()` 時 regenerate，並鎖定無 Session 成功路徑不會產生「已改成功卻回 500」。
- F3 有效：Self password Request 原先靜默忽略其他帳號流程欄位。已對 name、username、Email、角色、狀態與員工欄位等使用 `missing` rule 明確回 `422`，並同步 API 契約。
- F4 不採納：一般自助改密碼時，password 與 `updated_at` 被遮蔽後 before／after 為 null 是預期的敏感資料保護；既有 Audit row 與 Resource 仍保存／輸出 actor、subject、`PATCH`、`api/me/password` 與時間，足以辨識誰在何時執行專用改密碼操作。已補回歸測試鎖定此證據，不新增企劃外 marker 或 action。

第二輪 review：

- F5 有效：`current_password` 的 `string` rule 失敗後仍會執行 `current_password:web`，陣列輸入可能進入 `password_verify()` 而成為未處理的 `500`。已在規則鏈首加入 `bail`，並以 list、巢狀物件、boolean 與 integer 驗證全部回欄位 `422`，密碼與 flag 均不變。
- `UpdateCurrentUserProfileRequest` 的 name／username 非字串輸入已由既有內建型別規則安全回 `422`，沒有相同的 Hash check／TypeError 路徑，因此不擴改。
